## 二、各优化项评估指标

### 2.1 LayoutCalculator + Hysteresis

**优化目标**：防止锚点在阈值边缘（0.33/0.67）反复跳变

#### 评估指标

| 指标 | 定义 | 计算公式 |
|------|------|----------|
| 锚点跳变率 | 相邻两次生成中锚点变化的比例 | `跳变次数 / 总生成次数` |
| Offsets稳定性 | 相邻生成的Offsets差异（像素，预留，当前不写入报告） | `mean(abs(Offsets_new - Offsets_old))` |
| 边界区域稳定性 | 元素中心在阈值附近时的锚点一致性 | `一致次数 / 边界区域测试次数` |

#### 对比实验设计

```
基线组：无Hysteresis的简单阈值判断
  if (center < 0.33) anchor = 0.0
  else if (center < 0.67) anchor = 0.5
  else anchor = 1.0

实验组：带Hysteresis的锚点选择（含Buffer缓冲区）

测试输入：
  - 构造元素中心在 0.31~0.35 范围内微调的100组Bounds
  - 构造元素中心在 0.65~0.69 范围内微调的100组Bounds
  - 模拟多轮迭代场景（同一元素位置微调±0.02）
```

#### 预期收益

- 锚点跳变率：从 ~30% 降至 <5%
- Offsets稳定性：方差降低 50%+

### 2.2 ViewportMapping

**优化目标**：解决不同纵横比/分辨率下的坐标映射问题

#### 评估指标

| 指标 | 定义 | 计算公式 |
|------|------|----------|
| 映射往返误差 | Bounds → Slot → Bounds 的误差 | `max(abs(Bounds_out - Bounds_in))` |
| 跨分辨率一致性 | 同一设计在不同分辨率下的相对位置误差 | `abs(Norm_1080p - Norm_4K)` |
| 黑边处理正确性 | Fit模式下边缘元素的映射准确度 | 人工验证 + IoU |

#### 对比实验设计

```
基线组：直接 Bounds * DesignSize
  PixelX = Bounds.X * DesignSize.X
  PixelY = Bounds.Y * DesignSize.Y

实验组：ViewportMapping处理
  - Stretch模式：直接映射
  - Fit模式：计算黑边偏移后映射

测试输入：
  - 16:9 截图 → 16:9 目标（同比例）
  - 21:9 截图 → 16:9 目标（宽屏适配）
  - 4:3 截图 → 16:9 目标（窄屏适配）
  - 2560x1440 → 1920x1080（分辨率缩放）
```

#### 预期收益

- 映射往返误差：0px（数学精确）
- 跨分辨率一致性：归一化坐标误差 <0.001

### 2.3 Fixer规则修复器

**优化目标**：自动修正对齐、越界、等距问题

#### 评估指标

| 子功能 | 指标 | 计算公式 |
|--------|------|----------|
| 对齐吸附 | 对齐误差减少量 | `mean(abs(偏差_before)) - mean(abs(偏差_after))` |
| 越界修正 | 越界元素消除率 | `1 - (越界数_after / 越界数_before)` |
| 等距分布 | 间距方差减少率 | `1 - (Var(gaps)_after / Var(gaps)_before)` |
| 综合 | 修正有效率 | `符合规则的元素数 / 总修正元素数` |
| 综合 | 过修复率 | `破坏设计意图的修正数 / 总修正数` |

#### 对比实验设计

```
基线组：AI原始输出直接使用

实验组：经过Fixer处理
  - 对齐吸附：SnapPx = clamp(minDim * 0.002, 2, 6)
  - 越界修正：子元素裁剪到父容器内
  - 等距分布：行/列分组后组内等距

测试输入：
  - 包含 2-5px 对齐偏差的元素组
  - 包含越界子元素的容器
  - 包含 3+ 个近似等距元素的行/列
```

#### 预期收益

- 对齐误差减少量：平均 3-4px
- 越界元素消除率：100%
- 间距方差减少率：>80%
- 过修复率：<5%（需人工标注验证）

### 2.4 Prompt简化 + Bounds格式

**优化目标**：AI只做识别，不做像素计算

#### 评估指标

| 指标 | 定义 | 计算公式 | 目标阈值 |
|------|------|----------|----------|
| 布局MAE | 平均绝对误差（像素） | `mean(abs(actual - expected))` | ≤4px |
| 布局P95 | 95分位误差（像素） | `percentile(errors, 95)` | ≤8px |
| 元素召回率 | 识别出的元素数 / 实际元素数 | `TP / (TP + FN)` | ≥90% |
| 元素精确率 | 正确识别的元素 / 识别出的元素数 | `TP / (TP + FP)` | ≥90% |

#### 对比实验设计

```
基线组：旧Prompt
  - AI直接输出 Anchors/Offsets
  - Prompt ~200行，包含锚点计算指令

实验组：新Prompt
  - AI只输出 Bounds（归一化坐标）
  - Prompt ~50行，聚焦识别和分类
  - 程序端 LayoutCalculator 计算 Slot

测试输入：
  - 标准测试集（50-200张HUD截图）
  - 每张图片有人工标注的 Ground Truth JSON
```

#### 预期收益

- 布局MAE：从 ~15px 降至 ≤4px
- 布局P95：从 ~30px 降至 ≤8px
- 元素召回率：从 ~80% 提升至 ≥90%

### 2.5 JSON Schema Strict

**优化目标**：消除JSON格式漂移，减少解析失败

#### 评估指标

| 指标 | 定义 | 计算公式 |
|------|------|----------|
| 首次解析成功率 | 首次返回即可解析的比例 | `首次成功数 / 总请求数` |
| Schema合规率 | 符合Schema的响应比例 | `通过校验数 / 总响应数` |
| 平均重试次数 | 达到可用输出的平均重试次数（预留，当前不写入报告，需 Python 返回元数据） | `sum(重试次数) / 总请求数` |
| Token消耗 | 平均每次生成的Token数（预留，当前不写入报告，需 Python 返回元数据） | `sum(tokens) / 总请求数` |

#### 对比实验设计

```
基线组：宽松JSON模式
  response_format: { type: "json_object" }
  - 仅保证输出是合法JSON
  - 不保证符合Schema

实验组：严格Schema模式
  response_format: { type: "json_schema", json_schema: {...} }
  - 保证输出符合预定义Schema
  - 支持的提供商：OpenAI, Anthropic, Gemini

测试输入：
  - 相同的100次生成请求
  - 记录每次请求的解析结果和重试次数
```

#### 预期收益

- 首次解析成功率：从 ~85% 提升至 >99%
- Schema合规率：从 ~90% 提升至 100%
- 平均重试次数：从 ~0.3 降至 ~0.01
- Token消耗：减少 10-20%（减少重试）
> 说明：重试次数与 Token 消耗目前未在代码中采集，需 Python 返回元数据后再验证。

### 2.6 _meta字段支持

**优化目标**：提升调试能力，显式化不确定性

#### 评估指标

| 指标 | 定义 | 计算公式 |
|------|------|----------|
| 低置信度预测准确率 | confidence<0.8 的元素中实际有问题的比例 | `实际问题数 / 低置信度标记数` |
| 问题定位时间 | 从发现问题到定位根因的时间 | 用户测试计时 |
| 不确定属性命中率 | uncertain_props 中实际需要修正的比例 | `需修正数 / 标记数` |

#### 对比实验设计

```
基线组：无_meta信息
  - 调试时需要逐个检查元素
  - 无法快速定位问题来源

实验组：有_meta信息
  {
    "_meta": {
      "confidence": 0.85,
      "source": "ai",
      "uncertain_props": ["FontSize"]
    }
  }

测试方法：
  - 用户测试：给定问题场景，记录定位时间
  - 统计分析：对比 confidence 与实际错误的相关性
```

#### 预期收益

- 低置信度预测准确率：>70%（低置信度元素确实更可能有问题）
- 问题定位时间：减少 50%+
- 不确定属性命中率：>60%

## 四、实施建议

### 4.1 测试集构建

1. **来源**：UMG快速搭建 → 截图 → 标注JSON
2. **覆盖场景**：
   - 简单HUD（5-10个元素）
   - 复杂HUD（20-50个元素）
   - 边缘案例（贴边、重叠、等距排列）
3. **标注格式**：与AI输出Schema一致的Ground Truth JSON

### 4.2 自动化测试

```cpp
// 伪代码：自动化评估脚本
void RunPhase1Evaluation()
{
    TArray<FTestCase> TestCases = LoadTestSet("TestData/Phase1/");
    
    for (const auto& TestCase : TestCases)
    {
        // 基线运行
        FResult BaselineResult = RunPipeline(TestCase, EMode::Baseline);
        
        // 优化后运行
        FResult OptimizedResult = RunPipeline(TestCase, EMode::Optimized);
        
        // 计算指标
        FMetrics Metrics = ComputeMetrics(BaselineResult, OptimizedResult, TestCase.GroundTruth);
        
        // 记录结果
        LogMetrics(TestCase.Name, Metrics);
    }
    
    // 生成报告
    GenerateReport();
}
```

### 4.3 持续集成

- 每次代码提交自动运行评估
- 指标回退时阻止合并
- 定期更新测试集覆盖新场景

## 五、风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 测试集偏差 | 评估结果不代表真实场景 | 持续扩充测试集，覆盖更多HUD类型 |
| 过拟合测试集 | 优化针对测试集而非通用场景 | 保留验证集，定期更换测试集 |
| 人工标注误差 | Ground Truth不准确 | 多人标注 + 交叉验证 |
| 指标定义模糊 | 不同人计算结果不一致 | 明确计算公式，提供参考实现 |

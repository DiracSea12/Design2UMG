## H 级发现核实 - Batch 2

| # | 发现 | 结论 | 理由 |

| 10-H1 | `Design2UMGConverter.cpp` 中 Convert 通过 TSharedPtr 绕过 const FDesignDocument& 语义，静默修改调用者原始数据 | ✅ 确认 | `Convert` 签名为 `const FDesignDocument& Document`，但 `Document.Children` 中的 `TSharedPtr<FDesignNode>` 指向的对象是可变的。第282-283行 `Child->X = 0.0f; Child->Y = 0.0f;` 直接修改原始节点坐标；`PreComputeFitContentSizes` 大量回写 `Node->Width.Value`/`Node->Height.Value`（如第896-898行、第914-917行、第975-976行）。`const` 只保护了 `TArray` 容器本身不被增删，`TSharedPtr` 指向的 `FDesignNode` 完全可变。调用者如果复用同一个 `FDesignDocument` 多次调用 `Convert`，第二次会拿到被污染的数据。 |
| 10-H2 | `Design2UMGConverter.cpp` 中 static TSet WarnedFamilies 非线程安全，同文件已用 thread_local 说明有多线程预期 | ✅ 确认（严重性降级为 Medium） | 第752行 `static TSet<FString> WarnedFamilies;` 是普通 `static`，非 `thread_local`。同文件第16-18行有 `thread_local int32 GConvertNodeDepth/GPrecomputeDepth/GEstimateDepth`，说明代码确实考虑了多线程场景。但 `WarnedFamilies` 仅用于去重警告日志，竞态最坏结果是重复打印一条 Warning，不会导致崩溃或数据损坏。问题真实存在，但实际影响有限，建议降级为 Medium。 |
| 11-H1 | `VisualMapper.cpp` 中 Angular 渐变被当作 Radial 处理，fallthrough 到 Radial 分支 | ✅ 确认 | 第73-75行 `case EPenGradientType::Radial:` 和 `case EPenGradientType::Angular:` 共享同一个 `MaterialRef = MatRef_Radial;`。Angular（角度渐变）和 Radial（径向渐变）是完全不同的渐变类型，Angular 应该沿角度方向变化而非从中心向外扩散。同样的问题在 `WrapWithMultiFill` 第491-492行重复出现。这是一个功能缺失——没有 Angular 专用材质，fallback 到 Radial 是有意的近似处理，但确实会导致 Angular 渐变渲染不正确。 |
| 11-H2 | `VisualMapper.cpp` 中多 Shadow 效果只保留最后一个，同 key 覆盖前者无警告 | ✅ 确认 | 第166-199行的 Effects 循环中，Shadow 分支对非文本节点使用 `Widget.Properties.Add(TEXT("BoxShadowOffsetX"), ...)` 等固定 key。`TMap::Add` 在 key 已存在时覆盖旧值。如果一个节点有多个 enabled 的 Shadow 效果，循环会依次写入同一组 key，最终只保留最后一个 Shadow 的参数，前面的被静默丢弃。文本节点的 `ShadowOffset`/`ShadowColorAndOpacity` 同理。没有任何警告日志提示丢弃。 |
| 14-H | `LayoutFixer.cpp` 中 `FixEqualSpacing` 边界检查硬编码 0.0~1.0 归一化范围，像素坐标输入时等距功能静默失效 | ❌ 误报 | 第470行 `if (NewX >= 0.0f && NewX + Bounds[Idx].W <= 1.0f)` 看似硬编码，但查看调用链：`UMGWidgetUtils.cpp` 第758行注释明确写道 "Fixer内部假设归一化坐标系"，第761行 `NormalizeFixerBounds(FixerRoot, InvW, InvH)` 在调用 `FixWidgetTree` 前将像素坐标归一化到 0-1，第768行 `DenormalizeFixerBounds` 在调用后还原。`FixWidgetTree` 第512行 `RootParent = {0.0f, 0.0f, 1.0f, 1.0f}` 也印证了归一化坐标系。0.0~1.0 边界检查是正确的设计。 |
| 15-H | `LayoutValidator.cpp` 中 FBounds 定义为像素坐标，但误差计算函数当归一化值使用（乘以 DesignSize），接口契约矛盾 | ❌ 误报（存在文档歧义但非 bug） | `FBounds` 注释写的是"像素坐标"，但 `CalculateBoundsError` 将差值乘以 `DesignSize` 转换为像素——这说明函数期望输入的是归一化坐标（0-1范围）。这与 Fixer 的归一化坐标系一致：Fixer 输出的 Bounds 是归一化的，Validator 在 Fixer 之后对归一化 Bounds 做验证是合理的。真正的问题是 `FBounds` 的注释"像素坐标"与实际多处使用归一化坐标的情况不一致，属于文档/注释问题，不是逻辑 bug。且当前代码中未找到 `CalculateMetrics` 在生产路径中的调用点（仅在测试中使用），影响进一步降低。 |

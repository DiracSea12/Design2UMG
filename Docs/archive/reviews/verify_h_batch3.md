## H 级发现核实 - Batch 3

| # | 发现 | 结论 | 理由 |
|---|------|------|------|
| 18-H | `SerializeSlot` 未序列化 `bAutoSize` 字段，往返后 Size To Content 静默丢失 | ✅ 确认 | `FUMGSlotData` 在 `UMGSchema.h:113` 声明了 `bool bAutoSize = false`。`SerializeSlot`（UMGJsonSerializer.cpp:35-72）序列化了 Anchors、Alignment、Offsets、Padding、HAlign、VAlign、SizeRule、FillWeight、Row/Column/Span，但完全没有写出 `bAutoSize`。同时 `ParseSlotData`（UMGJsonParser.cpp:221-303）也没有读取 `bAutoSize`。而 `bAutoSize` 在 LayoutMapper.cpp:50、UMGGenerator.cpp:115、UMGSlotApplier.cpp:40、UMGWidgetUtils.cpp:441-452 等多处被实际使用。Serialize→Parse 往返确实会丢失此字段。 |
| 19-H | `NextRequestId` 无锁递增，`CallToolAsync` 回调在 HTTP 线程，数据竞争 | ❌ 误报 | `NextRequestId++` 出现在 `SendRequest`（cpp:76）和 `CallToolAsync`（cpp:256）中，两处都在构建请求体阶段执行，而非回调中。`SendRequest` 是同步阻塞 Game Thread 的方法（cpp:126-159 的 while 循环）。`CallToolAsync` 的 `NextRequestId++`（cpp:256）也在函数入口处执行，即 Game Thread 上。回调 lambda（cpp:276-304）中不访问 `NextRequestId`。头文件注释明确写了"不支持并发调用，必须等上一次完成后再发起下一次"（MCPHttpClient.h:32,41）。在约定的单次调用模式下，`NextRequestId` 始终在 Game Thread 上递增，不存在数据竞争。这是设计约定而非缺陷。 |
| 20-H | `NodeIds` 未对冒号做 URL 编码，与 Figma 官方要求的 `0-1` 格式不一致 | ❌ 误报 | Figma node ID 内部格式为 `数字:数字`（如 `123:456`）。`ExportImages`（FigmaHttpClient.cpp:24）直接用 `FString::Join(NodeIds, ",")` 拼接后放入 `?ids=` 参数。Figma REST API 官方文档实际上接受冒号原样传递（`?ids=1:2,3:4`），这是 Figma API 的标准用法。所谓 `0-1` 格式（用连字符替代冒号）是 URL path segment 中的替代表示，不适用于 query parameter。冒号在 URL query string 中是合法字符（RFC 3986），不需要编码。 |
| 23-H1 | `FindMissingFonts` 精确匹配 vs `FindFontAssetPath` 模糊匹配，逻辑不一致导致误报缺失 | ✅ 确认 | `FindMissingFonts`（cpp:60-98）调用 `ScanProjectFontAssets`（cpp:115-130）收集项目字体，后者只存 `Asset.AssetName.ToString()` 原始名称，然后用 `ProjectFonts.Contains(Family)` 做精确匹配（大小写敏感的 TSet 查找）。而 `FindFontAssetPath`（cpp:24-53）做了两层模糊匹配：IgnoreCase 比较 + 空格转下划线的 SafeFamily 比较。这意味着一个字体如 "Noto Sans" 在项目中资产名为 "Noto_Sans" 时，`FindFontAssetPath` 能找到它，但 `FindMissingFonts` 会报它缺失。两个函数对同一字体的判断结论矛盾。 |
| 23-H2 | `DownloadToFile` 主线程同步阻塞最多 30 秒 | ✅ 确认 | `DownloadToFile`（cpp:132-175）使用 `while (!bDone)` 循环 + `FPlatformProcess::Sleep(0.01f)` 阻塞等待，超时 30 秒。与 `MCPHttpClient::SendRequest` 不同，这里没有 `FSlateApplication::Get().PumpMessages()` 和 `Tick()`，也没有 `FScopedSlowTask` 进度条。编辑器 UI 在下载期间完全冻结，用户无法取消操作。对于远程字体下载这种网络 I/O，30 秒的无响应冻结是实际问题。 |
| 24-H | `Rasterize` 的 `Outer` 参数从未使用，纹理始终创建在 TransientPackage | ✅ 确认 | `Rasterize` 签名接受 `UObject* Outer`（PenPathRasterizer.h:23, cpp:554），但函数体（cpp:549-642）中 `Outer` 从未被引用。纹理通过 `UTexture2D::CreateTransient(Width, Height, PF_B8G8R8A8, NAME_None)`（cpp:613）创建，始终在 TransientPackage 中。调用方 `UMGPropertyApplier.cpp:203` 传入了 `I`（UImage 指针）作为 Outer，但该值被完全忽略。注释（cpp:617-620）解释了这是有意为之——Rename 到 widget 下会导致 mip 丢失，所以纹理必须留在 TransientPackage。参数存在但不使用，属于 API 误导。 |
